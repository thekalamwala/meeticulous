# Project audit — 2026-11-12

Full-codebase audit of `release/2026-11` (25 commits ahead of `main`), run per
[`PROJECT_AUDIT_GUIDE.md`](../PROJECT_AUDIT_GUIDE.md). This file is the **review list**: everything
found that was *not* fixed, because it needs a product, security, money or data decision.
**Nothing below has been changed.** Each item waits for approval.

Evidence levels: **V** = the lead read the code or queried the live DB directly ·
**R** = a reviewer read the full code path and the lead did not re-read it ·
**L** = likely, depends on something that could not be checked from here.

## Critical

### C1. Signed-in users can write sensitive columns straight to the database — V (live DB)
Old RLS policies plus table-wide grants to `authenticated` let anyone with a session call the
public Supabase REST API with the publishable key and their own token, bypassing the server:

| Table | Policy | What a user can do |
|---|---|---|
| `profiles` | `Users can update own profile` (no `WITH CHECK`, no column limit) | Set own `plan`, `plan_expires_at`, `is_verified`, `is_banned`, `role`, `subscription_status` |
| `bookings` | `Participants can update bookings` | Host or guest sets `payment_status`, `status`, `vendor_amount`, settlement/transfer fields |
| `payout_requests` | `Hosts can create payout requests` | Insert a payout request for any amount, skipping balance and KYC checks |
| `reviews` | `Authenticated users can create reviews` | Review any host with no booking |
| `services`, `products`, `availability` | own-row insert/update/delete | Skip plan limits, price floor and category validation |

No trigger guards these columns. The client never reads or writes tables through Supabase (auth
and realtime only — confirmed by grep), so these policies serve nothing.
**Impact:** free Pro, self-verification, self-marked-paid bookings, inflated payouts. Exposure
today is small (6 profiles, 0 bookings) but this must close before paid launch.
**Fix:** one migration that drops the write policies above and revokes INSERT/UPDATE/DELETE on all
`public` tables from `anon` and `authenticated` (keep the column-limited SELECT from v3.205 and the
public read policies still wanted). Add a test like `lockdownAnonRpcMigration.test.js`.
**Risk:** none expected for the app (server uses the service role). Needs a live-DB migration.

### C2. Phone-account takeover through `send-otp` — V
`server/controllers/authController.js:1012-1034` keys the OTP on the phone when one is supplied but
also emails the code to whatever `email` is in the request. `verifyOtpLogin` (`:1248-1272`) then
accepts that code for the phone and mints a full session.
**Exploit:** `POST /api/auth/send-otp {phone: victim, email: attacker}` → read the code in the
attacker's inbox → `POST /api/auth/verify-otp-login {phone: victim, otp}`. Works for any guest and
any host with a phone on file (dual login is one identity). Superadmin is refused.
**Fix:** issue login codes under their own OTP type, delivered to the phone only; never email a
phone-keyed code to a request-supplied address. **Risk:** the booking flow sends both email and
phone today, so the booking OTP path needs the same care (see H1).

### C3. Webhook marks a booking paid from `notes.booking_id` alone — V
`server/controllers/paymentController.js:1492-1507` calls `finalizeBookingCapture` with the
booking id from the payment notes, without checking the payment's order id or amount against the
booking. `createRescheduleFeeOrder` (`:1007`) writes the same `booking_id` into its notes, so a
₹50 reschedule-fee payment on an unpaid ₹5,000 booking flips it to paid and credits the host
(needs `reschedule_fee` ON — it is). **Fix:** resolve the booking by
`razorpay_order_id = payment.order_id`, assert the amount, skip when `notes.kind` is set.

### C4. Plan switch grants a full period before any payment — R
`paymentController.js:829-837`: on a switch, `plan` and `plan_expires_at = now + credit + full
period` are written before the mandate is authorised, and the old subscription is already
cancelled. Abandoning checkout leaves the host on Pro for the whole period; the orphan reconciler
never reverts the expiry. **Fix:** grant at most the credit days at create time; extend only on a
real charge; have `releaseOrphan` restore the prior expiry.

### C5. Nudge de-duplication is broken, and those nudges are live — V (code + live DB) — ✅ FIXED + flags off
> **Resolved 2026-11-12.** The 7 flags were flipped OFF on the live DB, and the dedupe is fixed in
> this PR: a shared fail-closed `utils/notificationDedupe.js` queries the real `event_key` (and a
> `payload->>dedupe_key` stamped by the engine for per-booking / per-user nudges). Safe to re-enable
> the flags once this ships. Original finding below.

Seven "already sent?" checks filter `notification_logs` on columns that do not exist (`event`,
`metadata`, `recipient_user_id`; the table has `event_key, channel, destination, status, response,
error, payload, created_at`). The query errors, the code reads only `data`, so the answer is always
"not sent". Files: `activationNudges.js:40-49`, `dormancyNudges.js:46-55`,
`festivalGreetings.js:55-65`, `humanMoments.js:49`, `empathyScans.js:48`, `reviewNudges.js:32-39`,
`community/onboardingSequence.js:47-54`.
All of these flags are **ON** in the live DB. `COMMUNITY_ONBOARD_HOT` already shows 4 sends to
2 recipients in 14 days. Volume is low only because there are few users.
**Immediate mitigation (your call, one SQL update):** turn the seven flags off until fixed.
**Fix:** filter on `event_key`, treat a query error as "already sent" (fail closed); review and
onboarding dedupe need a key that is actually written — a small design decision.

## High

**H1. Unverified phone on `PUT /api/auth/me` exposes other guests' bookings — R.**
`authController.js:1439` stores any phone with no OTP proof; `bookingController.js:851-857` returns
every booking whose `guest_phone` matches its last ten digits. Any user can set a victim's number
and read their bookings. Fix: phone settable only through an OTP-verified path; match by `guest_id`.

**H2. `verify-product` rejects every paid product purchase — V.** `paymentController.js:949`
charges `price + fee + GST on fee`; `:1183` expects `price + fee`. The buyer pays, sees
"verification failed", and only the webhook delivers. Fix: include `platform_fee_gst` and pass the
full order notes through.

**H3. Payout and refund maths read the live `services.price` — R.** Bookings store no service-price
snapshot; `bookingCapture.js:46,60,81` and five other sites recompute from the current service
row. A price edit between booking and payment, or a coupon, mis-credits the host. Fix: snapshot
`service_price` at creation (migration) and read only that.

**H4. Manual Route payout has no claim — double click pays twice — R.**
`routeTransferService.js:90-116`. The auto-payout rail already has `claimTransfer`; reuse it.

**H5. Concurrent cancels stack refunds — R.** `bookingController.js:891-894` +
`refundService.js:91-101`: two parallel cancels in the 6–24 h window each refund 50%.
Fix: conditional update, claim the refund on the row.

**H6. Refunded bookings stay withdrawable — R.** `settlementService.js:52-58` counts
`vendor_amount` whenever `settlement_status='eligible_for_settlement'`, and refunds never change
that status. Only the human approver stops a payout for a refunded booking.

**H7. A guest can reschedule a session that already started or ended — R.**
`bookingController.js:1414-1447` never checks the old `scheduled_at`. Free second session.

**H8. WhatsApp STOP opt-outs are mostly lost — R/L.** `whatsappWebhookController.js:57-63` matches
`contacts.phone` in `91XXXXXXXXXX` form; contacts store the raw phone. The update hits zero rows
and still answers `opted_out`. Root cause: five phone normalisers with three output formats.

**H9. Brevo bounces and complaints are never ingested — R.** All CRM and campaign mail goes through
Brevo, but only a Resend delivery webhook exists; `sendBudget.js` counts `provider='resend'`, so
the cold bounce circuit-breaker watches the wrong provider.

**H10. CRM mail can leave Brevo with a Resend-only From domain — R.** `crm/emailService.js:106`
forces the marketing provider; the admin composer and bulk email pass no sender, and the
documented "off switch" for `crm_shubham` / `crm_tithi` falls back to the `team.` domain instead
of stopping the send.

**H11. With `crm_admin_sends` off, sequences burn through silently — R.** `crm/sendGate.js:81`
returns `sends_disabled` without deferring; enrolments advance and complete with zero sends.

**H12. Session tokens get overwritten with stale copies — R.** `client/src/context/AuthContext.jsx`
`:120-125` (boot merge) and `:316-320` (`updateUser`) spread an old snapshot over freshly refreshed
tokens, causing a forced logout later — typically right after a plan upgrade. One-line fix each:
merge onto the current `localStorage` value.

**H13. `pg` is a devDependency but required at runtime — R.** `server/middleware/rateLimitStore.js:24`
needs it when `RATE_LIMIT_STORE_URL` is set. Move to `dependencies`.

**H14. Deploy and CI gates that may not be running — L.** (a) `render.yaml:144` builds with
`npm ci && npm run test:unit` under `NODE_ENV=production`, which omits jest — either the live
build command differs or the gate is skipped. (b) `client/vercel.json:348` disables all git
deployments, so the PR-preview smoke gate described in the docs cannot fire. (c) `smoke.yml`
triggers only on `deployment_status`, which CLI deploys may not emit. Check the dashboards.

**H15. `reseed-bot-kb.yml` is live, not inert — R.** DEPLOYMENT.md calls it skipped on this repo;
its guard matches this repo. It clears and re-inserts the bot knowledge base on every push to
`main` that touches `docs/help`, non-atomically.

**H16. Migrations in the repo but not applied — V.** `v3.191_support_sla`,
`v3.203_admin_token_version` (admin session revocation does nothing until applied),
`v3.204_coupons`. None is urgent while its feature is off, but v3.203 is a security fix.

## Medium

- **M1. Legacy `verify-subscription` throws after activating the plan — V.**
  `paymentController.js:525` declares `breakdown` inside a `try`; `:606` and `:638` use it outside.
  Returns 500 after the upgrade is written. Hoist the declaration, or delete the legacy
  `/subscribe` + `/verify-subscription` pair (the client no longer calls them).
- **M2. `PRODUCT_PAYMENT` ledger entry is unbalanced by the GST on the fee — R.**
  `ledger/journalTemplates.js:159-185`. Paid product sales never reach the books.
- **M3. Payment captured after a hold is reaped is silently kept — R.** `bookingController.js:2129-2147`.
  Money taken, no booking, no refund, no alert.
- **M4. Late guest cancel leaves the retained money unowned — R.** Needs a product decision on who
  keeps the non-refunded share.
- **M5. Complete / no-show writes are unconditional — R.** `bookingController.js:1092, 1374`. A
  booking cancelled mid-batch is overwritten to `completed`. Add `.eq('status','confirmed')`.
- **M6. Stale-hold reaper may error on every run — L.** `.update().limit()` without `.order()`
  (`bookingController.js:2139-2147`). Check Render logs for "Pending-hold reaper error".

  `productController.js:238`.
- **M9. One regex match = 24 h IP ban, triggerable cross-site — R.** `middleware/security.js:465-498`.

- **M13. Eight long-interval sender jobs still on raw `setInterval` — R.** `server.js:364-445`. A
  24 h timer never fires on a host that restarts daily. Fix only after C5.
- **M14. CRM lifecycle engine — R.** Reads ignore errors and are unbounded (`lifecycleEngine.js:180`);
  leads beyond the first 500 are never scored (`:134`); re-enrolling a lead sends nothing.
- **M15. Lead fields injected unescaped into CRM email HTML — R.** `crm/messageService.js:37-51`.
- **M16. Weekly host recap bypasses unsubscribe and can double-send — R.** `weeklyHostRecap.js:109`.
- **M17. A host's support "resend" emails their latest guest — R.** `supportActions.js:37-95`.
- **M18. Client 401 handling — R.** A wrong admin password or 2FA code hard-reloads `/backstage`
  (`api.js:49-56`); any dead session redirects to `/login` even on public pages, losing an

- **M19. Product buyer stranded if verify fails; coupon totals disagree; upgrade double-click — R.**
  `ProductPurchase.jsx:192`, `ServiceBooking.jsx:1126/1576/1829`, `UpgradePlan.jsx:112`.
- **M20. `server/.env.example` documents 88 of 212 env vars the server reads — R.** Missing ones
  include `KYC_ENCRYPTION_KEY`, `UNSUBSCRIBE_SECRET`, webhook secrets. `render.yaml` lacks them too.
- **M21. Load-test tooling can target the only DB — R.** `scripts/lib/guard.js` checks `NODE_ENV`
  only; `performance.yml` would seed and delete rows wherever its secrets point.
- **M22. Docs contradict the code and each other — V/R.** Plan names in six places
  (`docs/ai-context.md`, `feature-map.md`, `database-schema.md`, `design-system.md`, `README.md`);

- **M23. DB advisors — V.** 14 RLS policies call `auth.uid()` per row; 30 foreign keys without an
